# 설계 노트

WageClock을 만들면서 실제로 만난 문제와 그때 내린 판단을 정리했다. 기능 소개가 아니라
**무엇을 왜 그렇게 결정했는지**에 대한 기록이다.

돈이 오가는 서비스라 대부분의 문제가 한 곳으로 모인다 — **부분적으로 실패했을 때 무엇을
믿을 수 있는가.**

---

## 목차

### [01. 비동기 블록 안에서 DB를 만지고 있었다](01-async-boundary.md)

일괄 정산은 `CompletableFuture`로 N명에게 병렬 송금한다. 그 블록 안에 외부 API 호출과 DB 쓰기가
같이 들어 있었다. 트랜잭션은 스레드를 넘지 않는데도.

- 비동기 블록에는 I/O만 둔다. 상태 변경과 DB 작업은 메인 스레드로 모은다
- 스레드 경계를 넘는 것은 값이어야 한다

`@Transactional`과 ThreadLocal · sealed interface의 분기 강제 · Processor 패턴과 self-invocation

---

### [02. 포트가 엔티티를 요구하고 있었다](02-transaction-boundary.md)

선지급 승인이 프로덕션에서 깨져 있었다. 테스트는 전부 통과하고 있었다. 원인은 그 자리가 아니라
포트의 시그니처에 있었다.

- 엔티티는 트랜잭션 경계를 넘지 않는다. 넘길 것은 값으로 만든다
- 락은 대상 필드를 건드리기 전에 잡는다

준영속 엔티티와 지연 로딩 · 1차 캐시가 락을 무력화하는 경우 · 헥사고날을 어디까지 적용했나

---

### [03. 락으로 덮을 수 없는 구간](03-lock-and-state.md)

동시성 문제를 네 종류 만났는데, 락이 답이었던 건 하나뿐이었다. 나머지는 잠글 행이 없거나,
잠글 시간이 너무 길거나, 애초에 잠글 필요가 없는 문제였다.

- 없는 행은 잠글 수 없다. 조건이 "~가 없어야 한다"면 기준점을 따로 골라야 한다
- 락은 트랜잭션이 끝나면 풀린다. 그보다 긴 구간은 상태로 덮는다

lost update와 전체 컬럼 UPDATE · write skew · 선점(`TRANSFERRING`) · 정산 중 잠금(`SETTLING`)

---

### [04. 돈이 나갔는지 모를 때](04-settled-and-unsettled.md)

송금 결과는 성공·실패·진행 중 셋이 아니다. 네 번째로 **모르는 상태**가 있고, 이것을 어떻게
다루느냐가 가장 많은 코드를 만들었다.

- 전문번호가 나가기 전의 실패는 확정 실패, 나간 뒤의 실패는 미확정이다
- 확정된 실패만 되돌린다. 모르는 것은 잡아둔 채로 둔다
- 모를 때는 안전한 쪽으로 틀린다
- 실패를 인지한 쪽이 기록을 남길 수 있으면 아웃박스, 아무도 남기지 못하면 스위퍼

전문번호 사전 발급 · 선지급 한도 계상 시점 · 도달 불가능했던 분기 · 고치지 않기로 한 결정

---

### [05. 통과하는데 틀린 테스트](05-tests-that-pass.md)

찾은 결함 중 상당수는 테스트가 있는 코드에 있었다. 커버리지가 낮아서가 아니라, 검증한다고
믿었던 것을 실제로는 검증하지 않고 있어서다.

- 목은 호출됐는지를 검증하지, 넘긴 객체가 쓸 만한지는 검증하지 않는다
- 셋업이 만드는 상태가 실제로 가능한 상태인지 의심한다
- 가드가 막는 상황이 실제로 발생 가능한지 확인한다
- 재현할 수 없는 실패의 처리 코드는 검증되지 않은 코드다

---

## 읽는 순서

01 → 02가 이어진다. 스레드 경계에서 세운 원칙이 트랜잭션 경계에서 지켜지지 않아 실제 버그가
난 흐름이다. 03과 04는 독립적으로 읽어도 되고, 05는 앞의 네 편에서 나온 사례를 테스트 관점으로
다시 본다.
